# Архитектура NanoLab

Статус: проектное решение, интеграция не реализована. Общим должен быть **язык исследований и доказательств**, а не вымышленная универсальная физическая модель.

## Поток исследования

```text
Цель пользователя + проверенный пакет знаний
                 ↓
Структурированная спецификация
                 ↓
Проверка модели, протокола, прав и бюджета
                 ↓
AiiDA: исполнение и происхождение данных
                 ↓
Научный адаптер → физический движок
                 ↓
Проверки → анализ → наблюдения → evidence
                 ↓
Оптимизатор / исследовательский агент
                 ↺
```

## Компоненты

| Компонент | Ответственность | Не должен делать |
|---|---|---|
| Knowledge registry | Источники, допущения, файлы, лицензии, проверенные протоколы | Превращать текст статьи в доказанный результат |
| Design registry | Конструкции и их версии, допустимые преобразования | Скрывать изменение топологии |
| Experiment compiler | Преобразовать цель в проверяемую спецификацию | Додумывать отсутствующие параметры |
| Policy validator | Ограничения модели, ресурсов, доступа и схем | Менять критерии в пользу результата |
| Scientific adapter | Подготовка входов, запуск, разбор, модельные проверки | Выдавать exit code за научную приёмку |
| AiiDA execution | Связать процессы, данные и результаты | Автоматически знать все внешние допущения |
| Analysis engine | Наблюдения, статистика, диагностические признаки | Смешивать физический разброс и ошибку оценки |
| Campaign controller | Очередь, бюджет, состояния, восстановление | Запускать бесконечные повторы |
| AI researcher | Предложение гипотез и следующих опытов, объяснение | Подменять вычисления языковой уверенностью |
| Component library | Функции, интерфейсы, границы и evidence | Объявлять изолированный компонент пригодным для любой сборки |
| KnowledgePack importer (планируется) | Точные версии источников, права, форматы, provenance, reproducibility gates | Считать опубликованную статью исполняемым пакетом без проверки входов |
| Component/Assembly specs (планируется) | Молекулярные порты, anchors, frames, topology edits, model compatibility | Подменять реальную molecular connectivity геометрической картинкой |
| Assembly compiler (планируется) | Сформировать проверяемую общую DNA topology/config, fail-closed | Обещать изготовимость или смешивать incompatible engines |
| Standard test rigs (планируется) | Контроли, нагрузки, циклы, integrity, coupling/back-reaction, uncertainty | Выдавать анимацию за доказанное действие или КПД без источника энергии |
| Candidate generator (optional) | Генерировать кандидаты, отдавать на независимый физический расчёт | Принимать prediction генератора за validated result |

AiiDA ведёт происхождение вычислений; внешние источники, версии агентов и дополнительные артефакты регистрируются явно. aiida-shell используется как возможный стартовый путь, а не как доказательство уже существующего NanoLab-плагина. [S05–S06](research/SOURCES.md).

## Новая прикладная вертикаль — построение DNA-механизмов (NL6/NL7)

[Маршрут Literature-to-Mechanism R1](control/LITERATURE_TO_MECHANISM_ROUTE_R1.md) задаёт будущие возможности, не утверждая их текущую реализацию. Исходная научная вертикаль остаётся DNA_COARSE_GRAINED: сначала импорт одного известного S17-привода/ведомого узла с exact versions, inputs, rights и алгоритмами измерений. Объект `MechanicalComponentSpec` добавляется к существующему `component-card.v1`, а не заменяет старые claims. `ports` должны иметь локальную геометрию, идентификаторы молекул и способ реального соединения цепей.

Узкий `AssemblySpec` compiler принимает явные связи и преобразования, выполняет fail-closed проверки молекулярной топологии/единиц/совместимости, выдаёт одну oxDNA topology/config плюс traceable mapping. Нельзя просто совместить meshes и объявить химическую связь. Подготовительные restraints, физическое нагружение и сигнал управления разделены в protocol.

Первое испытание — `driver → follower`: no-drive и no-load controls, load transfer, return/reversibility, repeated cycles, structural integrity, error modes, uncertainty. Уменьшенная модель механических DOFs обучается/калибруется по detailed runs, затем отдельно сравнивается с hold-out данными. Это `COMPONENT_REDUCED`, а не независимая универсальная физика.

Генерация геометрии через Generative SNUPI или многокомпонентные редакторы (MagicDNA) — необязательные инструменты; их выходы всегда должны пройти независимую проверку topology/model. GUI и автоматическая сборка произвольных деталей откладываются до работающего CLI. Успешная релаксация ≠ доказанная экспериментальная самосборка. Новые E5 runs заблокированы до NL5 acceptance и активации native Ubuntu U1/R2.

## Первый научный адаптер

scadnano/исходный формат → oxDNA-конструкция → проверки → подготовка → расчёт → oxDNA analysis tools/PyMBAR → oxView. Исходный экспорт должен проверяться на выбранной топологии: нельзя предполагать поддержку всех типов дизайнов и сохранение каждой особенности конструкции.

Прежде чем интегрировать всё, NL1 выполняет тонкий вертикальный сценарий одного расчёта. Он затем включается в AiiDA в NL2. Полноценный специализированный плагин пишется только при доказанной необходимости; до этого достаточно ограниченного адаптера вокруг зарегистрированного executable.

## Контракт адаптера

Адаптер объявляет supported representations, model ID/version, required inputs, admissible parameter ranges, observables, resource requirements, preparation stages, parser version, failure taxonomy и applicability checks. Ни один неподдерживаемый тип структуры не принимается молча.

Первоначальные границы: одна локальная поддерживаемая среда, один движок, один класс конструкции. Имена API и поля — на английском; описания и документация — по-русски.

## Представления и масштабы

`DNA_COARSE_GRAINED`, `ATOMISTIC` и будущие `COMPONENT_REDUCED` — разные представления. Простого списка координат недостаточно: важны топология, ориентации, граничные условия, зарядовые и другие модельные предположения.

Конверсия — отдельный процесс с mapping, единицами, потерями информации и проверками. Нельзя напрямую связать oxDNA с квантовым или атомистическим движком и объявить получившуюся цепочку мультифизически корректной.

## Будущие адаптеры

ASE + один проверенный потенциал/движок для наночастицы или поверхности; затем Quantum ESPRESSO для конкретной электронной задачи; позднее транспорт или микроскопия. Каждый адаптер получает независимый эталон. Базы материалов и ML-потенциалы подключаются по потребности сценария, не ради широты каталога.

## Данные и развёртывание

Первоначально AiiDA и обычное версионированное файловое хранилище. Крупные траектории — вне Git, но с контрольными суммами, ссылками, размерами и политикой хранения. Дублировать AiiDA собственной графовой СУБД не требуется.

Окружения движка, анализа и LLM разделяются. Секреты не входят в научные артефакты. Чат не является базой данных. Полная остановка агента не должна уничтожать информацию о ходе кампании.

Будущий интерфейс: CLI/notebook → небольшой browser UI → удалённый executor при необходимости. Kubernetes, микросервисы и собственный планировщик HPC не являются задачами первого MVP.
