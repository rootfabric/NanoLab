## Цель

Bounded-пакет: (1) закрыть накопленные validator-hardening кандидаты вердиктов NL2-001/NL2-002 (S003, digest-vs-blob, emit_run порядок, O1 stale storage_location, O2/F3 placeholder-timestamps, F-1/O3 campaign evidence-map схема), (2) зафиксировать схему provenance-цепочки и правила stop/resume/дедупликации/readback документом и machine-readable конфигом. AiiDA-интеграция НЕ входит в этот WO (см. «Не входит»).

1. **S003 (технический/научный статус)**: `experiment_cli` reject'ит `scientific_outcome=SUPPORTED` вне научной поверхности — technical terminal event (RUN_COMPLETED/RUN_FAILED_TECHNICAL/RUN_ABORTED/RUN_BLOCKED_ENVIRONMENT) не может нести SUPPORTED ни при каких условиях; SUPPORTED допустим только на `ANALYSIS_COMPLETED` при наличии verification-поверхности (непустой `artifact_refs` с существующим артефактом анализа). Fail-closed. Тесты: gap-кейс S003 (фикстура `s003_tech_with_sci_claim`) → FAIL с явной S003-ошибкой; легитимная verify-цепочка (terminal c `scientific_outcome: null` → ANALYSIS_COMPLETED c SUPPORTED + evidence) → OK.
2. **Digest-vs-blob**: новый режим `experiment_cli verify-digests <path> [--rev HEAD]` — сверка sha256/size каждой записи `artifacts.manifest.json` с фактическими git-блобами (не рабочей копией — урок autocrlf, VERIFIER NL2-001 §3). Пригоден как CI-чек. Прогон на E1-R1, E1-R2, E0-R4 → 0 mismatch.
3. **emit_run порядок** (корень F1, REPAIR_MAP_F1_R1 §5.1 — ОБЯЗАТЕЛЬНЫЙ фикс): `e0_runner.py::emit_run` пишет финальный `case_record.json` ДО записи `artifacts.manifest.json`; манифест патчится дайджестами финальных байтов + проверка digest-инвариантности schema-валидации. Тест: emit_run на синтетическом scaffold → 0 digest-mismatch манифест-против-байтов (включая `case_record.json`).
4. **work_cli**: полный 40-hex `subject_sha` для новых событий — подтверждение существующего валидатора (whitelist легаси уже покрыт тестами MINOR-2); placeholder-timestamps (O2/F3-класс): midnight-placeholder `T00:00:00Z` и константный copy-timestamp (≥3 события с одним значением) → **ошибка** (не предупреждение — обоснование в PROVENANCE_RECOVERY_R1 §6: F3/O2 реально вводили хронологию в заблуждение, а «0 warnings» используется как сигнатура позитив-контроля, т.е. warnings не гейтят).
5. **evidence-map.schema.v1.json (F-1/O3)**: схема синхронизирована с де-факто форматом принятых кампаний (E1-R1/E0-R4/E1-R2 — campaign-map конвенция; checkpoint-вид, описанный старой схемой, не материализовался ни в одном опубликованном документе). Минимальный честный путь: schema follow facts (кампании приняты; формат — конвенция). Прогон валидации на всех трёх published evidence-map → 0 ошибок.
6. **O1 stale storage_location**: `experiment_cli` проверяет, что `storage_location` in-Git формата (`experiments/…`) содержит сегменты `campaign_id` и `run_id` манифеста (55 stale записей E0-R2 имели сегмент кампании `E0-R1` при кампании `E0-R2`).
7. **Provenance/recovery**: `docs/research/PROVENANCE_RECOVERY_R1.md` (цепочка subject→seeds→inputs→binaries→runs→analysis→evidence-map; stop/resume — run ID не переиспользуется, RESUMED-маркер на RUN_CHECKPOINT нового run; дедупликация идентичной поверхности; readback-требования: чтение из git-блобов с digest-верификацией, CRLF-урок F-3) + machine-readable `config/infra/provenance-recovery.v1.json`.
