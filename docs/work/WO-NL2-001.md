## Цель

Первый прогон E0 «Проверка измерительного тракта» ([E0_PIPELINE_VALIDATION](../experiments/E0_PIPELINE_VALIDATION.md)): до того как результаты пойдут ИИ, измерительный тракт обязан обнаруживать неправильные входы, корректные единицы и раздельные статусы. В данной revision (E0-R1) трактом является контрольная поверхность контрактов NanoLab — машинные схемы (`config/control/harness/*.schema.v1.json`) и CLI-валидаторы (`scripts/harness/`), бит-в-бит зафиксированные на base; физический runtime ещё не реализован (`runtime_implemented = false`), engine-coupled случаи E0-дока (повреждённая топология oxDNA, оборванный trajectory) остаются вне R1 и документируются как ограничение.

1. **Недостающий контракт — пререгистрация E0**: `docs/research/PREREGISTRATION_E0_R1.md` (`E0-PROTO-R1`): полный перечень контрольных случаев, критерии каждого случая ДО прогона, семантика исходов, budget, stop conditions. Никаких tolerances «под результат»; новые схемы не создаются — только существующие (`artifact-manifest.schema.v1.json`, `experiment-run/event.schema.v1.json`, `work-*`), gaps документируются.
2. **Контрактный формат evidence — как в ремонте NL1-002 (R2 F-1..F-3)**: `artifacts.manifest.json` — форма-массив (`name/sha256/size_bytes/producer_run_id/subject_sha/storage_location`, +`producer_command`); `manifest.json` — полный набор машинных полей по `experiment-run.schema.v1.json` (включая `subject_sha`, `claim_ceiling`, `model`, `observables`, `stop_conditions`, `resource_budget`); события — с `experiment_id` и полным 40-hex `subject_sha`; `subject_sha` всех run-поверхностей = freeze-commit кампании; терминальное событие — последнее; `event_id` = имя файла.
3. **Контрольные семьи E0-R1** (каждый случай — уникальный run ID `E0-R1-<family>NNN`):
   - **NEG** (N001–N009): дегенеративные/пустые/повреждённые входы в валидаторы (пустой JSON, обрезанный JSON, пропуск обязательных полей, filename≠event_id, отсутствие WORK_ORDER_STARTED, битый sha256/subject_sha в артефактах, legacy объектная форма манифеста, терминал не последним, контракт exit-кода) → валидаторы обязаны fail-closed (ненулевой exit, никогда `ok:true`);
   - **UNIT** (U001–U002): конверсия T=20C→0.097717 — pinned-engine факт (`ENGINE_ENVIRONMENT_R1` §6, лог OBSERVED, commit `00dc7fb9`); механическая проверка: корректное значение принимается (полоса 5e-7 = половина ULP 6-й значащей цифры печати engine, фиксируется до прогона), кандидаты-подделки (20, 293.15, 0.29315, 0.0978) отвергаются; tier-2 — поиск ветки конверсии в pinned-исходниках (best-effort, при недоступности сети — документированная INCONCLUSIVE-заметка, tier-1 не зависит);
   - **GEO** (G001–G003): синтетические геометрии, явно помеченные SYNTHETIC (не физическая траектория), с аналитически известными значениями: расстояние √2 и угол 90°; нулевое плечо → класс `ANGLE_UNDEFINED` без числа (смена ориентации оси: 60°/120° предсказаны аналитически заранее); критерий |Δ| ≤ 1e-12;
   - **STATUS** (S001–S003): технический outcome ≠ научный conclusion: `ANALYSIS_COMPLETED` без `scientific_outcome` → FAIL; недопустимый словарь (`PASS` как scientific outcome) → FAIL; gap-проба S003: `RUN_COMPLETED` (технический терминал) с `scientific_outcome=SUPPORTED` — контрактное ожидание «инструмент разделяет техническое и научное»; фактическое поведение фиксируется как есть (если валидатор пропускает — это задокументированный gap-результат NOT_SUPPORTED, сохраняется, не чинится посреди кампании);
   - **POS001**: позитивный контроль — собственная опубликованная evidence E0-R1 (все run-каталоги + check-consistency) обязана проходить валидаторы чисто (exit 0, ok=true, 0 warnings).
4. **Исполнение**: машинный runner кампании (`tools/e0_runner.py`, frozen до прогонов) готовит scratch-копии фикстур, вызывает валидаторы как subprocess, фиксирует exit/stdout/длительность, пишет 0002/0003-события и artifacts.manifest.json контрактного формата; ручные timestamps заменены машинными (рекомендация review NL1-002). JSON дополнительно валидируется по схемам (`jsonschema 4.22.0`) там, где схема покрывает файл.
5. **Отрицательные результаты сохраняются** (hard rule): NOT_SUPPORTED/INCONCLUSIVE/FAILED_TECHNICAL не перезапускаются «до успеха»; повтор — только новый run ID с записанной причиной.
